# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Ansible Infrastructure-as-Code for the Ubuntu hosts defined in `inventory.yml`:

- **`vps`** — the public web host (all user-facing services behind Traefik + Let's Encrypt).
- **`jenkins`** — a separate CI/CD host that builds app images and deploys back to `vps`.
- **`w1`** — a personal agent host (Claude Code sessions): the `host_agent` monitoring role plus the `agent_host` tuning role. Run by hand, never from CI.

Entry points: `playbook.yml` (main VPS), `jenkins-playbook.yml` (CI host) and `w1-playbook.yml` (w1, by hand). Each plays a flat list of roles from `roles/` against a single host. There are **no role dependencies or cross-role imports** — execution order is exactly the order in the playbook's `roles:` list, so reordering it can break network/dependency assumptions (e.g. `traefik` must run before any role that joins the `proxy` Docker network). Every role in `playbook.yml` carries a tag matching its name, so `--tags <role>` re-runs one service; **tags do not make the order safe to ignore**, and a tag-scoped run skips whatever earlier roles set up (which is why the `decabot` role repeats miplata's Zot `docker_login`).

## Common commands

All commands assume `.vault_pass` exists at the repo root (gitignored) and that you run ansible **from the repo root** — `ansible.cfg` now sets `vault_password_file = .vault_pass` as a relative path, so from anywhere else it prompts. CI is unaffected: every Jenkins stage passes its own `--vault-password-file` (or `ANSIBLE_VAULT_PASSWORD_FILE`), which overrides the config; it logs a harmless `.vault_pass was not found` line and exits 0.

**Ad-hoc `ansible` still needs `-e @vault.yml`**, and that is not something the config can fix — `vars_files` is a play-level directive, so an ad-hoc module run never loads `vault.yml` and `ansible_host` fails with *"'vault_main_vps_ip' is undefined"*:

```bash
ansible vps -e @vault.yml -m shell -a "docker ps"          # works
ansible vps -m shell -a "docker ps"                        # 'vault_main_vps_ip' is undefined
```

Moving `vault.yml` to `group_vars/all/vault.yml` would auto-load it for ad-hoc runs too, at the cost of changing vars precedence repo-wide. Not done. Never commit `.vault_pass` or an unencrypted `vault.yml`.

```bash
# Install required Galaxy collections (only community.docker is required)
ansible-galaxy collection install -r requirements.yml

# Deploy main VPS
ansible-playbook playbook.yml

# Deploy Jenkins VPS only
ansible-playbook jenkins-playbook.yml

# Deploy w1 (by hand, staged; see "The w1 host")
# A plain run (no --tags) plays host_agent and every agent_host stage at once; it is not a runbook step (rule 11 of agent_host)
ansible-playbook w1-playbook.yml --tags <stage> --check --diff
ansible-playbook w1-playbook.yml --tags agent_host --check --diff
# A real ssh stage also needs -e agent_host_second_terminal=true

# Dry run (no changes) — the same thing Jenkins runs before real deploy
ansible-playbook --check --diff playbook.yml

# Lint (same config Jenkins uses; see .ansible-lint)
ansible-lint playbook.yml

# Syntax-only check
ansible-playbook --syntax-check playbook.yml

# Target one role on one host (useful when iterating)
ansible-playbook playbook.yml --tags <tag>         # only if tags are set
ansible-playbook playbook.yml --limit vps --start-at-task "<task name>"

# Health checks (idempotent; run these after every deploy)
ansible-playbook tests/health-check.yml
ansible-playbook tests/jenkins-health-check.yml
ansible-playbook tests/w1-health-check.yml

# w1 agent_host verification (not post-deploy health checks)
ansible-playbook tests/w1-agent-host-preflight.yml   # before staging, run from tmux
ansible-playbook tests/w1-agent-host-check.yml       # exits non-zero until the stages are applied
bash tests/w1-agent-host-gate.sh                     # offline pre-merge bar

# Edit encrypted secrets
ansible-vault edit vault.yml
ansible-vault view vault.yml

# First-time vault bootstrap
cp vault.yml.example vault.yml && ansible-vault encrypt vault.yml
```

CI (Jenkinsfile) runs: `galaxy install → ansible-lint → --syntax-check → --check → deploy → health-check`. CI deliberately omits `--diff`: template diffs print old and new `.env`/`grafana.ini`/`pdns.conf` contents, and Jenkins keeps those console logs forever. Vault password and SSH key are injected from Jenkins credentials (`ansible-vault-pass`, `vps-ssh-key`) — never write them to disk outside the build workspace. w1 is outside CI: nothing lints, checks or applies `w1-playbook.yml`; `tests/w1-agent-host-gate.sh` is the pre-merge bar.

## Architecture: how the pieces fit

**Configuration layering** (standard Ansible, worth noting the specifics here):

- `inventory.yml` — three hosts, `ansible_host` values come from `vault.yml` so the repo is safe to publish.
- `group_vars/all.yml` — everything non-secret and shared: domain/subdomain patterns, image pins, Docker network list, Traefik/Grafana/Jenkins/Zot hostnames, UFW rules, fail2ban tuning. **This is the first file to read when you need to know what image version or hostname a service uses.**
- `host_vars/{vps,jenkins}.yml` — per-host overrides. The Jenkins host overrides `ssh_allowed_users` (root vs. ubuntu), its UFW rule set (no DNS ports), and the Traefik dashboard hostname.
- `vault.yml` — AES256-encrypted. Holds secrets **and** identifying info (IPs, domain, ACME email, GitHub user).

**Traefik owns 80/443, and two things have taken it away before. Check both first when nothing on the box is reachable.**

1. **A host-installed web server winning the boot race.** The `caddy` deb was left on the main VPS from before the Traefik migration with its systemd unit **enabled**. On the 2026-07-09 reboot it grabbed 80/443, Traefik exited 128, and the entire public plane — grafana, miplata, metabase, zot, categorizer, vault, dns — stayed down for **19 days** with nothing alerting. The `traefik` role now stops, disables and **masks** `caddy`, `caddy-api` and `nginx` (`traefik_contending_services`) before it brings the stack up; masked rather than disabled because disabling still permits socket/dependency activation. Nothing is uninstalled and `/etc/caddy` is untouched, so it is reversible. **Do not remove that task**, and never `systemctl unmask caddy` on this host.
2. **A container that lost its network endpoints.** After that incident `docker start traefik` brought the container up *attached to no networks at all* — so it could not resolve `docker-proxy:2375` and its declared `ports:` were never published, while `docker ps` cheerfully reported `Up`. `docker_compose_v2` with `state: present` will not heal this, because the compose config hash still matches. The fix is a forced recreate: `cd /opt/traefik && docker compose down && docker compose up -d`. **Diagnose with `docker inspect traefik` and look for an empty `NetworkSettings.Networks` — an `Up` status proves nothing.**

**Service topology on the main VPS.** Traefik owns 80/443 and terminates TLS via ACME (HTTP-01). Every other service is a Docker Compose stack joined to the shared `proxy` network and exposed only through Traefik labels. Two Docker networks are pre-created (`group_vars/all.yml: docker_networks`): `proxy` and `miplata_db` (isolates Postgres/Redis from the reverse-proxy plane).

**What Miplata is (the app behind the role).** Miplata is a personal-finance / spending-analysis web app ("where is my money going?"). The source lives in a separate repo (`git@github.com:GonzMenSeb/miplata.git`) as a pnpm + turbo monorepo: `apps/api` (NestJS 11 + Prisma + BullMQ + JWT auth), `apps/web` (frontend served by nginx on port 80), and `packages/{db,parsers,shared}` — the `parsers` package handles uploaded bank-statement files, which is why the compose stack bind-mounts `/opt/miplata/uploads` into the API. The API also depends on `@anthropic-ai/claude-agent-sdk`, so AI-assisted transaction categorization is part of the product. Out-of-app analytics happen via Metabase (currently switched off, `metabase_enabled: false`) querying Postgres through the read-only `metabase_ro` role that this Ansible role provisions.

**Miplata deploy pipeline (important, easy to misread).** The Ansible `miplata` role does *not* build images — it only provisions directories, `.env`, `docker-compose.yml`, a Postgres read-only user, and a DNS record. Images are built by a separate Jenkins job (`miplata-deploy`) that pushes to the self-hosted Zot registry at `zot.web.<domain>`. On a fresh VPS those images don't exist yet, so `roles/miplata/tasks/main.yml` intentionally tolerates a failed `docker compose pull` (`failed_when: false`) and guards `up` / SQL provisioning with `when: miplata_pull.rc == 0`. The health-check playbook mirrors the same guard. This is deliberate — don't "fix" it by making the pull strict.

**What DecaBot is (the app behind the `decabot` role).** DecaBot is the Los Prompteros AgentSprint entry — a conversational agent that turns a described sporting expedition into a real, size-resolved, in-stock Decathlon cart via Decathlon's public UCP/MCP endpoint. Source is a separate repo (`git@github.com:GonzMenSeb/Los-Prompteros-Project.git`), Python 3.12 + Reflex 0.9.7 + `gemini-3.6-flash`. Read that repo's `AGENTS.md` before touching anything — it carries a load-bearing-facts registry of live-verified behaviour that must not be "fixed".

Three things about this role are easy to misread:

- **One container, one port, one router.** Reflex needs two ports in dev, but in `--env prod` it mounts the compiled frontend onto the backend's own ASGI app, so `8000` serves the page *and* the `/_event` websocket. There is no path-based split and no second router — resist adding one.
- **The image is domain-agnostic on purpose.** Its baked `api_url` is `http://localhost:8000`; the compiled bundle rewrites any localhost-family host to whatever origin actually served the page and upgrades `ws`→`wss`. **Do not "fix" it to `decabot_host`** — that would need one image per domain and buys nothing.
- **Access control is the app's own password gate, not a Traefik middleware.** `vault_decabot_password` → `DECABOT_PASSWORD` in `/opt/decabot/.env`, enforced in Python inside every handler that spends a Gemini call. **An empty `DECABOT_PASSWORD` disables the gate**, so never let that template render blank. Rotating it needs only a role re-run, no rebuild.

**There is no Jenkins job for DecaBot** — unlike `miplata-deploy` and `categorizer-deploy`, the image is built and pushed by hand from the app repo (see its `docs/DEPLOY.md`). Adding a `decabot-deploy` job is the obvious next step; until it exists, don't write docs that assume it. **Zot accepts OCI manifests only** — a plain `docker push` uploads every layer and then fails `manifest invalid` (`415`) at the manifest step, so pushes need `docker buildx ... --output type=image,oci-mediatypes=true,push=true`. As with miplata and categorizer, the role tolerates a failed pull on a fresh VPS; don't make it strict.

**DNS.** PowerDNS runs on the main VPS and is authoritative for the project domain. Roles that need an A record (like `miplata`) add it via `docker exec pdns pdnsutil replace-rrset <zone> <name> A 3600 <ip>` — note that `pdnsutil` takes the short `name` (relative to the zone), not the FQDN.

**PowerDNS-Admin is behind a GitHub-only gate, and its own GitHub login is not the gate.** `pdns-auth` (oauth2-proxy, `oauth2_proxy_image`) is the only Traefik router on `pdns_admin_host`; `pdns-admin` has no labels and is not on the `proxy` network, so no other container can reach it, and `tests/health-check.yml` fails if it joins. `--github-user={{ pdns_admin_github_login }}` with no org or repo set rejects every other GitHub login (`checkUserRestriction` in the v7.15.5 provider source, and tested against the real images with a fake GitHub). PowerDNS-Admin's own GitHub login has no allowlist: an unknown login gets an account and the first account ever becomes Administrator, so it is only safe behind the gate with the administrator pre-seeded (`roles/dns/files/seed-admin.py`, idempotent, run by `roles/dns/tasks/admin.yml`). The seed is also required because that login crashes with `None.lower()` for an account with no public email. Leave the proxy's scope at its default (`user:email read:org`): the provider lists the user's organizations on every login even with no org restriction, and GitHub answers 403 without `read:org`, which shows as a 500 on `/oauth2/callback` (seen on the first real sign-in, 2026-11-08). Local login and sign-up are off. One GitHub OAuth app serves both with two callback URLs, `/oauth2/callback` and `/github/authorized`. `vault_pdns_admin_github_client_id`, `vault_pdns_admin_github_client_secret` and `vault_pdns_admin_cookie_secret` must be in `vault.yml` before `vps-deploy` runs, or the play fails on an undefined variable. The blackbox probe targets `/ping`, because `/` now redirects to GitHub.

**Observability.** Prometheus + Loki + Grafana + Alloy + cAdvisor + blackbox-exporter all run as containers on the main VPS (`monitoring` role). The Jenkins host runs only `observability_agent` (Alloy + node_exporter) and *pushes* metrics/logs over the internet to `prom-push.<web_subdomain>` and `loki-push.<web_subdomain>`, which Traefik exposes with bearer-token auth (`vault_observability_push_token`). `node_exporter` is installed on the host, not in a container, so `base` role adds a UFW rule allowing Docker bridge subnets (172.16.0.0/12) to reach `:9100` — do not widen that rule.

**The `w1` host.** A personal box that runs Claude Code, with no Docker and no Traefik. `w1-playbook.yml` plays two roles against it, in two plays: `host_agent` (node_exporter and Alloy installed on the host, both bound to `127.0.0.1`), which pushes metrics and journald logs to the same `prom-push` and `loki-push` endpoints with `host="w1"`, and `agent_host` (network, memory, session and access tuning, applied in stages selected by the tags `agent_host_<domain>`). `observability_agent` cannot be reused: it hardcodes `host = "jenkins"` and would overwrite the Jenkins series. `w1` is its own inventory host (`vault_w1_ip`, user `ubuntu`), must never join `vps` or `jenkins`, and never uses the `base` role. It is not in any Jenkinsfile and `vps-deploy` does not touch it, so merging applies nothing to w1: apply it by stage with `ansible-playbook w1-playbook.yml --tags <stage>` (rule 11 of `agent_host`; the full staged procedure, rollback table and open decisions are in `w1-agent-host-runbook.md`), then run `tests/w1-health-check.yml`, all by hand. The panel's host list is hardcoded (`HOSTS` in `panel/src/views/model.ts`, the enum in `panel/src/manifest.ts`), so a new host needs a panel change; it must not get a `panel_services` entry, because every service needs a container. It shares `vault_observability_push_token` with the Jenkins host, so rotating that token means redeploying both hosts.

**`agent_host` rules.** (1) Layout: one defaults file per domain under `roles/agent_host/defaults/main/` and every variable defined once; short module names throughout `roles/agent_host` (`copy`, `template`, `command`, like `host_agent`; never `ansible.builtin.` there); the lint bar is `Passed: 0 failure(s), 0 warning(s)` under the repo's profile `min` (the production-profile line that `ansible-lint` also prints is vacuous under `min`, so never cite it as a result). Stages are `import_tasks` lines in `tasks/main.yml`, each with its tag; `agent_host_live` marks tasks that need systemd, the network or a running daemon and is skip-only (the container lab skips it; never give it to `--tags`, never skip it on w1). There are no handlers: live state converges in tasks, because a handler notified before a failing task is lost and the re-run then reports `changed=0`; so no `notify:`, `flush_handlers`, `force_handlers` or `reset_connection`. `w1-playbook.yml` has two plays so that a failing `agent_host` stage cannot drop the pending `host_agent` handlers. Sysctl converges with `sysctl -p` of the role's own `/etc/sysctl.d/60-agent-host-<domain>.conf`, never `--system`. (2) The sshd guard: the hand-made `/etc/ssh/sshd_config.d/00-no-password.conf` is adopted byte for byte and is the only thing keeping passwords off (cloud-init writes `PasswordAuthentication yes` and root has a usable password); sshd takes the first value it reads, so never delete or rename it and never rely on `60-cloudimg-settings.conf`. The role owns `10-agent-host-auth.conf` and `11-agent-host-transport.conf` with disjoint keys; `agent_host_ssh_protected` keys (root login, `AllowUsers` and kin, port, listen address, `MaxAuthTries`) stay unchanged unless unlocked in `agent_host_ssh_unlocked_keys`; auth ships `AuthenticationMethods "publickey"`. (3) The ssh apply: the stage plans first with `check_mode: true` tasks and enters its arm, write, reload and probe block only when the plan, an armed timer or a stale daemon says so (otherwise it prints `sshd stage: nothing to apply`, so a converged real re-run is `changed=0`); `agent_host_second_terminal` is asserted before the block and only when there is something to apply, never inside it (a failing assert there would run the rescue and set the live drop-ins aside). Inside: `sshd -t`, `sshd -T` (it reports disk only), `reload` and never `restart`, the journal as the proof of the reload (never `ExecReload` start_time), then a fresh login plus `sudo -n true` plus a password-refusal probe over a separate connection; a dead-man timer runs `/usr/local/sbin/agent-host-sshd-rollback` if the controller dies; `--check` does not run `validate:`, so it proves rendering and not validity. (4) Ordering: limits then probe, ssh then probe, ufw last; `pam_limits` is `required` for sshd and sudo, so a bad limits line can reject every login; the limits line is soft-only (`nofile`, agent user, no `nproc`, no `*`, no `root`), and `DefaultLimitNOFILE` in the user-manager drop-in is always a `soft:hard` pair. (5) Network: the three `net.ipv4` keys are always rendered, so toggling BBR reverts live values; BBR applies to new connections only and the kernel ignores `tcp_slow_start_after_idle` for BBR sockets (the derived default is `1` under bbr and `0` under cubic); `tcp_bbr` is pinned in `/etc/modules-load.d/agent-host-net.conf`; ClientAlive lives in `11-agent-host-transport.conf` and is switched by `agent_host_ssh_transport_enabled`; `agent_host_mosh_udp_range` is the single source for any firewall rule; `mosh-server` refuses a client locale w1 has not generated (set `LC_ALL` on the client, or opt in with `agent_host_locale_extra`, and never commit the locale name); `tests/w1-net-lab.py` is a workstation lab; the 181 ms path is geography and no setting changes it. BBR and the ClientAlive keepalive are config only, apply to new connections only, have no measured improvement and no evidence gate was evaluated; with `agent_host_ssh_transport_enabled: true` a new raw ssh session whose peer vanishes is dropped after about 11 minutes instead of about 2h11m (sessions not hosted in herdr or tmux typically get SIGHUP); `agent_host_ssh_transport_enabled: false`, `agent_host_net_congestion_control: cubic` and `agent_host_net_slow_start_after_idle: 1` revert them. (6) Memory: swap is built with `fallocate` under a temp name and renamed, and the apply path never `swapoff`s or resizes an active swap file (an inactive wrong-sized one is deleted and recreated); only `agent_host_mem_state=absent` stops the swap unit, and only when used swap is below half of MemAvailable and memory PSI some avg10 is below 1.0; zswap is persisted by a tmpfiles rule, because a unit ordered before the swap unit forms an ordering cycle; earlyoom is off by default (`agent_host_mem_earlyoom_enabled: false`), dryrun first, with go-live only through a committed `host_vars/w1.yml` and never `-e` alone (the next plain run reverts it), triggers on MemAvailable alone, and its `--avoid` list comes from `agent_host_mem_earlyoom_avoid`; the `HostSwapping` alert is blind to zswap traffic. (7) Packages and reporting: apt only through `tasks/apt_install.yml` (`NEEDRESTART_MODE=l` and `NEEDRESTART_SUSPEND=1`), with two exceptions, an `update_cache`-only task after the gh source changes and the earlyoom purge in the rollback; the gh keyring pin guards a fresh host only (advisory row E14 notices a rotation, which is applied with `--tags agent_host_packages`); the apt module marks every requested package manual, so `changed=0` does not show that flip; the reboot-required gauge is visibility only. (8) Firewall: opt-in (`agent_host_firewall_enabled`, default `false`), a dead-man `agent-host-ufw-rollback`, never `ufw reset` or `ufw limit 22`; the first enable can stall quiet live flows; the fail2ban override (`agent_host_fail2ban_enabled`) bans only new connections; `ubuntu` has `NOPASSWD:ALL`, so the firewall guards against exposure and mistakes only, not against a compromised session. The firewall tasks have not been executed end to end against a real ufw (containers cannot load netfilter). (9) Reboot: the role never reboots (a kernel update leaves a pending reboot that kills herdr and every session); `w1-reboot-playbook.yml` is the only path: it prints what the reboot ends, stops unless `-e agent_host_reboot_confirm=<kernel GRUB boots by default>` and, for the real run, `-e agent_host_second_terminal=true` (a standing root session), refuses while dpkg or apt is busy or an apt timer is due within `agent_host_apt_timer_margin_minutes`, has no force flag and ends with the check play; GRUB is hidden on a BIOS guest, so confirm the provider rescue or console first; never restart `ssh.socket` or `user@*`. (10) Verification: `tests/w1-agent-host-check.yml` reads the role defaults through `include_role` (so `host_vars` overrides count), takes its evidence in one root login via `tests/files/w1-agent-host-collect.sh`, and takes rows from `tests/w1-agent-host-check-rows/<domain>.yml`; `W1_TARGET=<user>@<host> tests/w1-agent-host-bench.sh snapshot <label>` is the before/after record under `bench-out/` (gitignored); idempotence is `ansible-playbook w1-playbook.yml --tags agent_host --check --diff` and a real `--tags agent_host -e agent_host_second_terminal=true`, both `changed=0` (the full play's marker task changes on every run); `tests/w1-health-check.yml` skips its swap and gauge series tasks until w1 itself shows a swap total or the gauge timer, so it is not a stage prerequisite. CI never lints or runs w1, so `bash tests/w1-agent-host-gate.sh` (syntax, lint, isolation and hygiene greps, container lab, selftest) is the pre-merge bar. (11) Apply is manual and staged, from tmux with `ssh root@<host>` open in a second terminal: A `agent_host_packages,agent_host_locale,agent_host_network`; B `agent_host_memory,agent_host_sysctl,agent_host_session,agent_host_reporting`; C `agent_host_limits`; D `agent_host_ssh` (real run with `-e agent_host_second_terminal=true`); E `agent_host_firewall` (opt-in, enabled with `-e '{"agent_host_firewall_enabled": true}'`, real run with `-e agent_host_second_terminal=true`); F and G `--tags agent_host` (check, then real), then the check and health playbooks; H the reboot playbook. Every stage is `--tags <stage> --check --diff` and then the real run, and every `-e` given to a stage is repeated on its check. A `host_agent`-only change is applied with `--skip-tags agent_host`; a plain run is the whole role and needs `-e agent_host_second_terminal=true` whenever the ssh stage has something to apply. (12) Rollback (the durable form is a `host_vars/w1.yml` key committed on its own, because any later plain run undoes an `-e` or manual rollback):

- ssh: as root, `/usr/local/sbin/agent-host-sshd-rollback` (restores the guard's canonical bytes, sets `10-` and `11-` aside, `sshd -t`, reload); durable `agent_host_ssh_enabled: false`, or `agent_host_ssh_transport_enabled: false` then `--tags agent_host_ssh -e agent_host_second_terminal=true` for the keepalive alone. Never delete `00-no-password.conf`.
- net sysctl and BBR: `rm /etc/sysctl.d/60-agent-host-net.conf /etc/modules-load.d/agent-host-net.conf`, then `sysctl -w net.ipv4.tcp_congestion_control=cubic`; durable `agent_host_net_congestion_control: cubic` and `agent_host_net_slow_start_after_idle: 1`, then `--tags agent_host_network,agent_host_sysctl`.
- session sysctl (inotify): `rm /etc/sysctl.d/60-agent-host-session.conf`, then `sysctl -w` the before values from the snapshot; durable `agent_host_sess_sysctl: {}`, then `--tags agent_host_sysctl`.
- limits: `rm /etc/security/limits.d/60-agent-host.conf` (new sessions only); durable `agent_host_limits_enabled: false`.
- user-manager limits: `rm /etc/systemd/user.conf.d/60-agent-host.conf` (next user-manager start; never `daemon-reexec`); durable `agent_host_session_manager_limits_enabled: false`, then `--tags agent_host_session`.
- swap and zswap: `--tags agent_host_memory -e agent_host_mem_state=absent` (never `swapoff` under memory pressure); durable `agent_host_mem_state: absent`, then `--tags agent_host_memory`.
- earlyoom: `systemctl disable --now earlyoom`; durable `agent_host_mem_earlyoom_enabled: false` (the role then stops managing it but does not stop a running one: undo first), then `--tags agent_host_memory`.
- mosh: `apt-get remove mosh`; durable `agent_host_mosh_enabled: false`, then `--tags agent_host_network`.
- gauge: `--tags agent_host_reporting -e '{"agent_host_reporting_gauge_enabled": false}'`; durable the same key, then `--tags agent_host_reporting`.
- extra locale: re-comment the line in `/etc/locale.gen` and `localedef --delete-from-archive` it, never a bare `locale-gen`; durable `agent_host_locale_extra: []`.
- gh and baseline packages: nothing to undo on w1; on a fresh host `apt-get remove gh` and drop its apt source and keyring, with durable `agent_host_gh_enabled: false` and an edited `agent_host_baseline_packages`, then `--tags agent_host_packages`; the manual marks are undone with `apt-mark auto git curl tmux htop`.
- linger: nothing to undo on w1 (it was already yes); on a fresh host `loginctl disable-linger <user>`; there is no dedicated role switch, `agent_host_session_enabled: false` skips the whole session stage including the user-manager limits.
- firewall: `ufw disable` and `systemctl disable --now fail2ban` (the dead-man does the first after 300 s); durable `agent_host_firewall_enabled: false`.
- reboot: `shutdown -c` from the already-open root session inside the 60 s window; afterwards provider rescue or console.

**Jenkins container.** The `jenkins` role builds a local image (`jenkins-ansible:latest`) from `roles/jenkins/files/Dockerfile` + `plugins.txt`, then runs it via Compose. It grafts the host's `docker` group GID into the container at build/run time (`getent group docker` → `jenkins_host_docker_gid`) so the Jenkins user can talk to the host Docker socket. Jenkins config is fully declarative via JCasC (`roles/jenkins/templates/casc.yml.j2`); mutating state through the Jenkins UI will be overwritten on the next `ansible-playbook jenkins-playbook.yml`.

**`jenkins-playbook.yml` restarts Jenkins and kills any in-flight build.** "Deploy JCasC config" carries `notify: restart jenkins`, whose handler is `docker_compose_v2: state: restarted`. Because `casc.yml.j2` interpolates vault secrets, **editing `vault.yml` alone is enough to fire it** — no `.j2` file has to change. A `sh` step is a host process owned by the durable-task plugin, not the JVM, so it dies with the restart and the build fails `script returned exit code -1` with **no ansible error anywhere in the log** — Lint/Syntax/Dry Run all read green, then stop mid-task. Seen on `vps-deploy` #37, 30 Jul 2026, killed mid-Dry-Run by the `jenkins-playbook.yml` run that shipped `vault_jenkins_coros_ssh_key`. Quiet Jenkins down first, or just re-run the job afterwards; `durabilityHint`/`retry()` do **not** fix this and `retry()` would mask real failures.

**What the panel is (the `panel` role).** Internal admin web app (Bun + Hono) at `panel_host`, replacing separate logins to Zot, Traefik, PowerDNS-Admin, Jenkins and Grafana. The role is last in `playbook.yml` because it needs traefik, dns and zot first. Four things are easy to misread:

- **It is root-equivalent on the host.** It mounts `/var/run/docker.sock` and `/opt` (same absolute path, so `docker compose` in `/opt/<svc>` works) and joins the docker and `ssh_allowed_users` group GIDs via `group_add` (looked up with `getent` inside the role; `jenkins_host_docker_gid` is not shared across roles). Login is GitHub OAuth locked to `grafana_github_admin_login`.
- **`panel_services` in `group_vars/all.yml` is the single manifest.** The panel cannot read this repo, so `services.json.j2` renders the list to `/opt/panel/services.json`. When a role's container names, dir, hostname, image or Jenkins job change, update that list too. Jenkins-host services are read-only in the panel.
- **It joins the pdns compose network as external** (`panel_pdns_network`, `dns_dns_internal`) to reach the PowerDNS API on `pdns:8081`; PowerDNS is not on `proxy`.
- **Secrets:** `vault_panel_*` in `vault.yml.example`; the Zot login reuses `ci` / `vault_zot_registry_password`. `vault_panel_jenkins_token` is created by hand in Jenkins (JCasC cannot provision tokens). Like brujula, it logs in to Zot as both root and `ssh_allowed_users`, and tolerates a failed first pull; don't make it strict.

**Panel source and jobs.** The app lives in this repo under `panel/` (Bun + Hono; build context is `panel/`). `panel-deploy` (in `casc.yml.j2`) checks out this repo with `github-ssh-key` and runs `panel/infra/jenkins/Jenkinsfile`: tests, buildx OCI `:<sha>` + `:latest` into Zot at `panel/panel`, `compose up -d` on the VPS, `/healthz` check with auto-rollback to the previous revision label. It skips when nothing under `panel/` changed. Both `panel-deploy` and `vps-deploy` fire on every push to main (`githubPush`, one webhook); `vps-deploy` exits green early via its `Scope` stage when a push touched only `panel/`, and `panel-deploy` ignores anything outside `panel/`. The Jenkinsfile reads `REGISTRY`, `VPS_HOST` and `PANEL_URL` from the global env vars set in `casc.yml.j2`. Changes under `roles/panel` or `group_vars` are infra, not panel, and go through `vps-deploy`. Adding the job needs a Jenkins reload after the play (see the note above `jobs:` in `casc.yml.j2`).

**Agent host section.** The Hosts page adds an "Agent host" section for any host that reports `agent_host_*` series (`w1` today), read-only, from the `prom:agent` source (one Prometheus instant query at the same 15 s ttl as the host cards, plus four extra 24-hour series in `prom:series`). The settings table is whatever `agent_host_setting_ok{setting=...}` series exist, written by the `agent_host` role's settings gauge (`agent-host-settings-gauge.timer`, textfile `agent_host_settings.prom`) from the same variables its stages render; the panel only maps known ids to display names (`AGENT_SETTING_NAMES` in `panel/src/views/agent-model.ts`), so a new id shows up marked unknown until it is named there. The run timestamp is read with `last_over_time` over 24 hours, so a host that goes dark stays listed as not reporting instead of vanishing after Prometheus's 5-minute lookback.

**Editing credentials from the panel (`panel-secrets`).** The Auth tab reveals `.env` values and edits secrets without the panel ever holding the vault password or a GitHub token. An edit POSTs the Jenkins job `panel-secrets` (`infra/jenkins/panel-secrets.Jenkinsfile`, logic in `infra/jenkins/panel-secrets.sh`, started only by the panel) with `VAR_NAME` and `VAR_VALUE`. The job clones main with `github-write-ssh-key`, decrypts `vault.yml` with `ansible-vault-pass` into a tmpfs scratch dir, replaces that one top-level line, checks the decrypted result differs from the original in exactly that line, re-encrypts, commits a message naming only the variable, and pushes to main without force (it re-fetches and retries when main moved). The push fires `vps-deploy`, which applies it, and the panel keeps the credential "pending" until the `vps-deploy` build for that commit finishes.

- **The allowlist is explicit and fails closed.** `panel_secret_editable` in `group_vars/all.yml` lists every variable the job may edit, and `panel_secret_locked` lists every excluded one with its reason. Every vault variable in `panel_service_auth` (the `auth` block of every main-VPS service, split out of `panel_services` because templating `panel_services` needs image variables that only `playbook.yml`'s roles define, so the Jenkins play cannot render it) must be in exactly one of the two: the `panel` role asserts it, so adding a variable there fails `vps-deploy` until it is classified, and a variable in neither list, or in both, is read-only in the panel and refused by the job. `panel_secret_vars` (editable minus locked) is rendered into the job as `PANEL_SECRET_VARS` and into the panel's manifest as `secrets.editable`; a manifest without it allows nothing. The job's copy only changes when `jenkins-playbook.yml` runs, while the panel's changes with `vps-deploy`, so after unlocking or adding a variable, run the Jenkins playbook before expecting the edit to work. Locked means: anything also consumed by `jenkins-playbook.yml` (which `vps-deploy` never runs), the panel's own `vault_panel_*`, database passwords that Postgres/MariaDB read only on first init, and encryption keys. Unlock one only after checking that reason is gone.
- **Values are limited to `[A-Za-z0-9._~+=:@%^*!?,/-]`** (`SAFE_VALUE_SOURCE` in `panel/src/secrets/values.ts` and `safe_re` in `panel-secrets.sh`; a test keeps them identical, and rotate and the Generate button stay inside it). The value is written unquoted into `.env` files read by Docker Compose, into `grafana.ini` and into `pdns.conf`, where `$`, `#`, quotes, backslashes, `;` and spaces are rewritten, cut off or rejected (`ab$cd` becomes `ab`, a leading `'` makes Compose refuse the whole file). Each allowed character was checked against Compose v2.38, go-ini 1.67 (the version in Grafana 12.4.3) and `pdns_server` 4.9.13. Widen the set only after repeating that for every consumer in `panel_secret_editable`. Minimum lengths come from `panel_secret_min_length` and reach the job as `PANEL_SECRET_MIN` (`name:length` pairs) and the panel through its manifest, so both enforce the same numbers; the job refuses a vault edit when `PANEL_SECRET_MIN` is unset. The traefik hash line is exempt: the password is bcrypt-hashed and never reaches a parser.
- **Traefik dashboard** (`traefik_dashboard_auth`) is not in the vault. It is a bcrypt `user:hash` line in `group_vars/all.yml`, so `PANEL_HASH_VARS` makes the job edit that file instead, doubling every `$` for compose. The plaintext is never stored, so it can be changed but not revealed. The Jenkins host's own dashboard is not updated by `vps-deploy`.
- **`vault_jenkins_github_write_ssh_key`** feeds the `github-write-ssh-key` credential and must be a deploy key with write access, added to `vault.yml` before `jenkins-playbook.yml` runs (the template fails on an undefined variable). If main is branch-protected, the job's push is rejected and the build fails after 3 attempts.
- **`VAR_VALUE` is a core password parameter, stored encrypted in the build record**, because Job DSL has no `passwordParam` and `nonStoredPasswordParam` needs the Mask Passwords plugin; casc adds it with a `configure` block, and declares the parameters there so `buildWithParameters` works before the first run. Verified on a throwaway Jenkins 2.580.2: `/api/json` shows only the parameter's name, `build.xml` holds `{AQAAAB...}`, and the pipeline console does **not** mask it, so the job never prints it and runs `set +x`. Do not declare `parameters`, `disableConcurrentBuilds` or `buildDiscarder` in the Jenkinsfile; casc owns them.
- **The job's workspace is a checkout of this repo** (Declarative's implicit checkout), so the repo's `ansible.cfg` (`vault_password_file = .vault_pass`, `become = True`) applies to every ansible command run from it. `panel-secrets.sh` therefore pins `ANSIBLE_CONFIG` to a neutral file in its scratch dir; without that every edit died at the parse-back check with "vault password file .vault_pass was not found" (the first real edit, `panel-secrets` #1).
- **The scratch directory must be tmpfs.** The job writes the vault password and the decrypted vault under `/dev/shm` and stops rather than fall back to disk. The `sh` step runs under dash, whose EXIT trap does not fire on abort or timeout, so the stage also traps TERM/INT/HUP and `post { always }` deletes any `panel-secrets.*` directory left behind.
- **Accepted tradeoffs, in case this is reviewed again.** `github-write-ssh-key` is GLOBAL scope like every credential here, so any Jenkins job can bind it and push to main; jobs already hold `vps-ssh-key` and `ansible-vault-pass`, so per-job scoping would not be a real control. The panel runs as the Jenkins admin (`vault_panel_jenkins_token`). Re-auth is a silent OAuth redirect while the GitHub session is alive: it defends against a stolen panel cookie, not against someone at an unlocked browser. The Jenkins-side allowlist, minimums and the credential's description only change when `jenkins-playbook.yml` runs (and that restarts Jenkins). `VAR_VALUE` stays in the last 10 build records, encrypted with Jenkins' master key.
- Reveal reads `<dir>/.env` as the panel container (group `ssh_allowed_users`) and returns only the manifest's `env_keys`. It, and every edit, need a sign-in newer than `SECRETS_REAUTH_SECONDS` (15 min), and each is audited without the value.

## Terraform: OVH VPS provisioning (`infra/terraform/`)

Orders and terminates an OVH VPS from `terraform.tfvars` (`make up`, `make down`, run from that directory; see its `README.md`). OVH credentials are the `OVH_*` lines in `local.env` (gitignored), which the Makefile exports; the same values are in the vault as `vault_ovh_*`. The account is on the Canadian API (`ovh-ca`) with subsidiary `WE`.

- **Never import or reference the existing VPSes** (the main VPS at `vault_main_vps_ip`, and the stopped `vps-2025-model2` one) in the main configuration. `ovh_vps` forces replacement when its `plan` block differs, so an import plans a terminate of production. The one exception is `make retire`, which imports the old server into the separate throwaway `retire/` root only to terminate it.
- **`make up`, `make down`, `make backup`, `make migrate`, `make restore`, `make jenkins` and `make retire` change real servers and are not all reversible.** `apply` places a real order, `destroy` and `retire` request termination, `backup` stops every container on production, and `cutover` rewrites `vault_main_vps_ip` and runs the playbook. Do not run any of them without the user asking. `make plan`, `make test`, `make stock`, `make key`, `make images` and `make catalog` are read-only.
- **The API key's rights cannot be edited and it expires.** `make up` and `make down` run `scripts/check-key.sh` first, which compares the key's real rules (from `/auth/currentCredential`) with the list it needs; run it with `make key`. `make up` also runs `scripts/check-stock.sh` (`make stock`), so that no order is placed into a datacenter OVH reports out of stock (what OVH does with such an order was not tested).
- **A plan that terminates or reinstalls a server is blocked** by `scripts/check-destructive.sh` unless `ALLOW_DESTRUCTIVE=1`. Editing `image_id` or the SSH key reinstalls in place, and the provider saves state before the reinstall, so a failed reinstall leaves a paid, tainted VPS.
- **The generated Ansible host is `vespiridion`, never `vps` or `jenkins`.** Running `playbook.yml` against a new server would drive `cloudflare_dns` and `dns` with `vault_main_vps_ip`. The only sanctioned way to move production is `make cutover` (inside `make migrate`), which sets `vault_main_vps_ip` through `scripts/set-vault-var.sh` and runs the playbook. The runbook, rollback and the hazards are in the README section "Replacing the production server".
- **While a migration is in flight, `main` must not move.** `vps-deploy` and `panel-secrets` run `main`'s code and `main`'s `vault.yml`, so a push with the old `vault_main_vps_ip` deploys to the old server and `cloudflare_dns` points `ns1` back at it. `.backups/` holds the Vaultwarden database and TLS private keys; it is gitignored and mode 700.
- **Metabase and `llm_inference` are switched off** with `metabase_enabled: false` and `llm_inference_enabled: false` in `group_vars/all.yml`. Each role still runs: its `disable.yml` removes the containers and keeps the volumes. Keep both roles in `playbook.yml`, because the categorizer reads `llm_inference_model_id` from the `llm_inference` defaults. Alloy, the Prometheus rules and `tests/health-check.yml` skip them via the same flags.

## Conventions and gotchas

- **Every service lives under `/opt/<service>/`** on its host. Compose files, `.env`, and any bind-mounted state all live there. The default is set in each role's `defaults/main.yml` (e.g. `miplata_dir: /opt/miplata`).
- **`.env` files are rendered from `templates/env.j2`** via the Ansible `template` module with `mode: "0640"` and group-readable by `ssh_allowed_users`. Don't `copy:` env files — they must be templated so vault vars resolve.
- **Docker Compose v2 is the expected invocation** (`community.docker.docker_compose_v2`, `docker compose pull`). Don't fall back to the legacy `docker_compose` module.
- **`ansible-lint` profile is `min`** with several rules skipped (`command-instead-of-module`, `no-changed-when`, etc.) — intentional. Don't silently re-enable them in role changes.
- **Fact caching is on** (`ansible.cfg`: jsonfile in `.ansible_facts_cache/`, 1h TTL). If you add a task that depends on a fresh fact you just changed on the host (e.g. a new group membership), use `meta: clear_facts` or `gather_facts: true` explicitly.
- **Ubuntu user differs per host**: `ubuntu` on main VPS, `root` on Jenkins — templates that bake in a user should read `ssh_allowed_users`, not hard-code.
- `docs/` is gitignored (planning notes with identifying info are kept local-only). `vault.yml.example` is the canonical template for onboarding.
